Release 0.6.7 - Fix: TT compile cache can no longer break rendering

Three field-report fixes from the 0.6.5/0.6.6 incident round. All gates green;
channel: edge.

Rendering resilience
- An unwritable lazysite/cache/tt subtree no longer takes the site's layouts
  down. Template Toolkit 2.x treated a failed .ttc compile-cache write as a
  fatal render error (every page silently downgraded to the built-in fallback
  layout - the manager stuck at "Loading..."); TT 3.x dies outright (a 500).
  The processor now retries the render once without the on-disk compile cache.
- A manager-layout failure is LOUD: the fallback page carries a red
  ls-layout-error banner naming the template error. Public pages keep the
  silent fallback - template errors never leak to visitors.
- lazysite-check probes cache/tt for dirs the CGI cannot write; --fix removes
  the tree wholesale (a pure cache - it regenerates on the next request).

Manager fixes
- The Users page called recent-changes through the users sub-dispatcher, which
  rejects it - audit noise ("user-recent-changes ... Unknown action") and the
  recent-change dots never loaded. It now calls the top-level action.
- The plugin-save audit records the keys that ACTUALLY changed: a site-title
  edit now reads "lazysite (site_name)", not "lazysite (8 settings)".
