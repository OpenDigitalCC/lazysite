Release 0.9.9 - BETA: data-loss + security hardening, disabled-service messaging, dormant-capability hints

Channel: BETA. Reliability and security hardening on the 0.9.x beta line, plus a
manager-UI improvement. No BREAKING changes, no migration. Operators should
upgrade.

Data-loss hardening (file writes):
- FIX: concurrent config saves could truncate lazysite.conf to a single line (a
  non-atomic truncate-before-lock writer racing the Services page's parallel
  saves). Writes are now atomic (temp + rename, never unlinking the real file);
  config-set holds a lock across its read-modify-write.
- FIX: the same class in the AUTH STORE - write_users / write_groups /
  update_user_hash / the MCP form-bind / the bad-URL caches now write
  atomically, and every auth-store mutation serialises on a store lock, so a
  reader never sees a truncated credential store and concurrent edits cannot
  lose an update. Reads (verify-credential) stay lock-free.

Security hardening (reported privately; specifics in the advisory):
- SECURITY: manager file-path confinement. The file-editor path blocklist is now
  matched against the CANONICAL resolved path, closing a traversal by which a
  content-authoring account could reach engine-owned files under lazysite/.
  Operators should upgrade.
- SECURITY: file-download and zip-download now enforce the same per-file read
  ACL and dav_scope confinement that the read action applies (previously they
  enforced neither), so a delegated editor cannot pull a file restricted away
  from them.
- SECURITY: the account/group roster (principals) is now capability-gated
  (manage_content or manage_domains) - a user with no grant-related capability
  can no longer enumerate every account and group.
- FIX: manage_domains / feedback / read_submissions grants were resolved but not
  surfaced to the cookie-manager capability gate, so a NON-operator grant of any
  of them silently did nothing (read_submissions shipped inert in 0.9.8). All
  three now take effect; a parity test pins the capability set so a future grant
  cannot go dormant.

Clearer disabled-service response:
- FIX: a switched-off service (token exchange) answered HTTP 404 - which reads as
  "endpoint not deployed" and misdirected diagnosis. It now answers 200 with
  {ok:0, code:"service_disabled"}, matching the control API.

SM180 - dormant-capability indicators:
- The Groups and Users capability grids flag a channel capability granted while
  its site service is switched off ("granted, but the X service is off
  site-wide - enable it in Settings -> Services"), so a dormant grant is visible
  instead of silently doing nothing. Indicate, don't block - no migration.

Full gate before the build: suite + bench + coverage (every production CGI above
floors).
