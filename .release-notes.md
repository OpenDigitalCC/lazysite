# 0.10.3 - EDGE

**The MCP surface reaches parity, and the platform stops accepting bad
instructions quietly.**

An edge build on 0.10.2. The theme is the agent-facing surface: an MCP partner
could not do several things a token client could, and in the places where the
two surfaces did agree, nothing kept them agreeing. Alongside that, three changes
close cases where lazysite accepted an instruction that was wrong and reported
success.

No BREAKING change and no migration. One behaviour change worth knowing about:
installing a layout now appears in content history, because it writes to the site
config and every write to that file is now recorded.

## An MCP agent can manage domains, and scope its work to one

`domain-set` existed on the control API and nowhere else, so a partner working
over MCP had to ask an operator to bind a layout or theme to a sub-domain - or be
issued an API token purely to reach one action. The MCP surface now carries
`list_domains`, `domain_set` and `preview_domain`.

`activate_theme` and `activate_layout` gain a **`host`** parameter. Without it
they act instance-wide, as before; with it they act on that domain alone. This is
the case a multi-domain agent kept getting wrong, because the instance-wide call
was the only one available and it looked like the right one.

## An MCP agent can write binary files

`write_file` carries text. Uploading a logo, a favicon or a photograph meant
falling back to WebDAV with a separate credential, which is why several sites
have images an agent could not replace. `upload_file` takes base64 content and
writes it through the same guarantees - locks, content history, ACL checks - as
every other write.

## The two surfaces are now held together by a test

The gaps above were each found by a partner hitting one. Nothing was checking, so
each was found the expensive way, one at a time.

`t/lint/23-mcp-api-action-parity.t` now maps every control-API action to its MCP
tool and fails when one gains an action the other does not have. Where a surface
legitimately stands alone - 24 API-only actions, 13 MCP-only tools - the entry
carries the reason, and a stale entry that no longer matches anything is also a
failure.

Running it for the first time found something else: **13 control-API actions were
absent from the capability model's `unlocks` lists**, so `describe_capabilities`
under-reported what every one of those capabilities actually grants. An agent
reading its own permissions was told less than it had.

## A missing parameter is no longer read as an instruction

`theme-activate` with the theme name in the wrong parameter stripped the site's
theme and returned `ok:1`. The control API defaults `path` to `/`, the name
sanitiser reduces `/` to the empty string, and the empty string meant
*deactivate*. A site agent did exactly this to a live site and caught it only by
checking `theme-list` immediately afterwards.

An empty name is now an error naming the right parameter. Deactivation still
works and now requires asking for it: `deactivate=1`.

## Warnings arrive where the mistake is made

The briefings already say all of this. The problem a partner named is that an
agent reads a briefing once and then works through a tool surface that cheerfully
accepts the thing the briefing warned against.

`write_file` and `create_page` now warn - never refuse - on a page body carrying a
full HTML document, a `<style>` block, or baked-in navigation chrome, each naming
the alternative rather than only the prohibition. `create_theme` warns on a theme
that hides layout chrome or sets content transparent by default, including the
`prefers-reduced-motion` rule that reads like a safety net and is not one.

Setting an `@group` ACL now warns that a group entry matches manager users only -
token, MCP and WebDAV partners carry no groups, so a rule written to include them
silently excludes them.

**A rename now reports the alias its old URL needs**, and writes it with
`add_alias`. Retiring a URL without aliasing it is how twenty legacy URLs were
lost on one site and recovered by hand afterwards.

## audit_site reports what the site already knows about itself

Every starter page carries a provenance marker that nothing had ever read.
`audit_site` now reports the starter pages still present and how many of them are
in the sitemap - the ratio is what makes an untouched scaffold obvious at a
glance.

## One write path for the site config

Two pieces of code wrote `lazysite/lazysite.conf` by different mechanisms, and
only one of them recorded the write. Changing a setting through the manager
appeared in content history; registering a domain did not, and the guarantee
suite could not see the gap because it was not looking at that module.

The commit is a property of writing the file, not of the action that happened to
do it, so it now lives inside the single writer that all callers share. Layout
installs gain a content-history entry as a direct result. A site-package apply
sets several keys and now records one entry rather than none.

## Also

An `appearance` page shipped with a literal NUL byte in it, which made git treat
the page as binary - no reviewable diff, and no grep would find anything in it.
Removed, with a lint test so no shipped page can carry a control character again.
The "in use" marker on that page is also stated once rather than twice.
