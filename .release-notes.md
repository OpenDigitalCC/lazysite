# 0.10.4 - EDGE

**Things that reported success without doing the work, and files that never
reached the visitor they belonged to.**

An edge build on 0.10.3. Most of this release is one theme: an operation answered
`ok`, the caller believed it, and the thing asked for had not happened. Each was
found by someone acting on that answer and discovering the truth later, usually
expensively.

## BREAKING: `list_versions` returns `versions`

It returned `entries`. A reporting agent read that as zero versions and began
writing it up as a defect - it was returning two, perfectly well. **A wrong key
and an empty result are indistinguishable**, so the failure is not an error but a
confident wrong conclusion, and the natural next step is filing a bug against
working code.

There is no deprecation window. Edge sites meet this first and stable is
untouched until it promotes, so there is time to find integrations before it
reaches them.

Only that one key changed. `list_domains`, `form-list` and `theme-list` already
named their contents, and `list_content_history` still returns `files` because it
genuinely returns a list of files with revision stats - renaming that would make
it less accurate, not more.

## Success reported for work that did not happen

**`add_alias` on a rename** wrote nothing when the page had no front matter, and
still returned `ok` with the alias reported - which reads as "added". Front
matter is optional, and an old hand-written page is both the most likely to lack
it and the most likely to have a published URL worth keeping. It now creates the
block, and the result distinguishes *written* from *already there* from *could
not*.

**`preview_domain`** returned `ok` unconditionally. It discarded the processor's
stderr and never checked its exit status, so a dead processor, an empty render and
a genuinely blank page were one indistinguishable answer. A tool whose whole
purpose is verification should not report success without verifying; it now names
which of the three happened.

**`theme-activate` and `layout-activate`** take the name in a parameter called
`path` - the file-ish parameter everywhere else - so callers send `theme=`, which
used to sanitise to empty and mean *deactivate*. 0.10.3 made that an error; this
release accepts the obvious spelling, so the trap is no longer reachable.

**The form timing token** was minted when a page rendered and then baked into the
cache, so every visitor shared one timestamp. Measured on a live site: three
fetches two seconds apart returned the same token, already 363 seconds stale, and
a submission with no dwell at all was accepted. The check could not tell a
visitor who read the page from a client that never fetched it. It is now minted
per response, and a page carrying a form is no longer publicly cacheable.

## A secondary domain's own files now reach its visitors

**The per-domain registries** - `sitemap.xml`, `llms.txt`, `robots.txt`, the
feeds - were generated correctly per domain and never served. Every routing rule
in the shipped vhosts is conditioned on the request mapping to no file, which is
right for pages and exactly wrong here: the primary's `sitemap.xml` exists, so the
web server answered with it for every host. All four templates now route those
five paths to the engine unconditionally.

**This needs an operator action on an existing site.** Templates apply at install
time, so a deployed vhost keeps the old routing until it is regenerated or the
lines are added by hand.

**A 404** now belongs to the domain that was asked. It resolved the error page
against the primary's docroot, so a mistyped URL on a secondary domain showed the
primary's branding and navigation. It also carries the baseline security headers
now - previously the one response most likely to be reached by a scanner was the
only one served without them.

**Deleting a page** cleared the registries for the docroot only, so on a
multi-domain instance the domain's own sitemap kept the deleted URL until its TTL
expired. That looked like slow convergence; it was a refresh aimed at the wrong
file.

## An agent can tidy up after itself

An agent holding `manage_themes` could create a theme and had no way to remove
one, so every experiment was permanent and only the operator could clear it.
`delete_theme` now lets a caller remove **what it created and nothing else** - a
theme it did not create, or one that predates the field, stays an operator
action. The active-theme and in-use protections are unchanged and still come
first.

## Information a partner should not have

`audit_site` returned the server's absolute filesystem path - including the
hosting account name - to every token and MCP client. One line was responsible,
and that same line meant **the stale-HTML audit had never run at all**: it
reported exactly one finding, always the docroot it was supposed to start
scanning from.

A new sweep checks the whole read-only partner surface for filesystem paths,
because the next leak will not be in the field anyone is watching.

## Seeing what the configuration does not say

`audit_site` also reports **static files a protected site is serving to anyone**.
An operator who sets `auth_default: required` watches every page bounce to the
login form and reasonably concludes the site is closed - while a `.html` or a PDF
with no page source is served to anyone who knows the path. This release
**detects** that; it does not yet refuse it, because enforcement would start
turning away assets on live sites and that decision has not been taken.

## The manager

**Adding a domain uses the same sheet as configuring one.** They were the same
object described twice, with two copies of every field. The create-only parts -
copy settings from an existing domain, seed a home page, derive the site address
as you type - all survived the move, and the add form's better field help came
with it.

## Also

- The docs now state which variables a page body may use. `[% theme_assets %]`
  resolves in a layout and silently becomes empty in content, which cost an agent
  a whole handover; `validate_page` now warns where the mistake is made.
- The forms doc names the URL that actually accepts a submission - posting to the
  page returns 200 and stores nothing, which is indistinguishable from success.
- `site_apply` can take the package's identity on MCP and the CLI, not only the
  control API. The default is unchanged: the target keeps its own address.
- New guards: dead paths in documentation, backlog status against the CHANGELOG,
  registry routing in every vhost template, one conf writer, one domain form.
- `docs/MANUAL-CHECKS.md` records the nine areas the test suite cannot reach and
  the manual pass that covers each - because "all tests passed" reads like "it
  works" and is not the same claim.

## Upgrading

`list_versions` callers must read `versions` rather than `entries`. Existing
vhosts need regenerating to pick up the registry routing. Nothing else needs
action.
