# SM158 - Portable per-domain site packages

An agency builds a demo site on a shared instance and hands it to a client who
wants their own instance; or a site moves from one domain to another. Before
SM158 the only portable snapshot was the whole-docroot `full` backup, which
carries every client and the auth secrets - so it is a system-user operation,
not self-service, and not per-site.

A **site package** is one domain's site, and nothing else.

## What travels

Content
: the domain's `content_root` subtree (pages + assets).

Navigation
: the domain's `nav_file` OVERRIDE only. A base-inherited nav is left to the
  target (its own base nav applies); the manifest records `nav: base-inherited`.
  Keeps the package out of the shared infra.

Theme + layout
: the referenced layout directory, pruned to the one theme the domain uses, so
  a shared layout does not drag other clients' themes along. Self-contained, so
  the package applies on an instance that never had that layout.

Manifest (`site.json`)
: the source host, the presentation keys (site_url, site_name, theme, layout,
  nav_file, search_default), and the nav mode.

## What is deliberately excluded

Plugins, instance/site settings and **any secret** (auth, form keys). A package
therefore carries no secrets and is safe to hand over - which is why, unlike the
`full` backup, this is self-service.

## The round-trip

create (export)
: `package_create($host)` writes `lazysite-site-<host>-<stamp>.tar.gz` into the
  backups area. Download it with the normal backup tooling.

upload (import)
: a multipart upload stores a package into the backups area - the first backup
  *upload* (backups were server-only). Only needed when moving between instances.

apply
: `package_apply` extracts to an ISOLATED staging dir (never straight onto the
  docroot) with the SEC-2026-07 M-TAR flags, drops any symlink member, and
  rejects any path that resolves outside the stage. It then copies the vetted
  content into the target content root (confined; optional `clean`), installs the
  bundled layout/theme only when the target lacks it (never overwrites a shared
  layout), places the nav, and writes the target domain's keys. The control-API
  action takes a safety snapshot first and commits the result to content history
  (parity with `backup-restore`).

## Surfaces

- Control-API: `site-backup-create`, `site-backup-upload`, `site-backup-apply`.
- MCP: `site_backup`, `site_apply`, and the `migrate-site` recipe in
  `describe_capabilities` -> `tasks`.
- CLI: `lazysite-site backup|apply`.

All gated by **`manage_domains`** (SM160) + scope access to the content root.

## Capability (SM160)

Domains and this site-package family are their own capability, `manage_domains`,
carved out of the broad `manage_config`. See
[SM160]. Applying a package reconfigures a domain, so it is domain management -
not the broad instance-config capability, and not plain content editing.

## Docs

## Out of scope

DNS, the web-server domain alias and TLS for the new domain remain the operator's
/ Hestia's job - set them up first (the domain Check confirms them), then apply.
