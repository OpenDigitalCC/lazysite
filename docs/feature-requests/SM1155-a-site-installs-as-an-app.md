# What happened

L1, filed 2026-10-17 by the OOM agent at the owner's request, from the pocket
portal evaluation:

> A site, or a section of a site, can be installed on a phone or tablet as a
> progressive web app, as the present JPM pocket portal (a Vue PWA) is. [...]
> lazysite's docs name no web app manifest and no service worker.

What the present PWA needs, measured: a manifest with name, short name, theme
colour, icons 64, 192 and 512, a maskable icon, a start URL and a scope; a
service worker that precaches the shell, serves scripts and styles
stale-while-revalidate and images cache-first, and updates itself; no offline
queue, background sync or push.

Constraints from the Odoo extension (SM747, SM857): the worker never caches the
Odoo endpoint, a page with an `odoo:` or `odoo-identity:` binding, or any
per-viewer page, and never stores the session or identity cookies, tokens or
answers.

L1 asked whether the manifest and worker are site-level, section-level or both;
whether they are engine assets; how icons are supplied; and how the worker's
version follows a deploy.

# The rulings

The release manager accepted these on 2026-10-17 ("all rulings accepted"):

Both levels
: Site-level (scope `/`) and section-level (a scope under a path), from
  `lazysite.conf`: `app_name`, `app_short_name`, `app_theme_colour`,
  `app_background_colour`, `app_start_url`, `app_scope`. One app per domain;
  a domain's own settings override as `alias.<host>.app_name` and so on.

Engine assets
: The manifest and the worker are generated by the engine from the settings,
  never hand-authored under `/lazysite-assets/`. Served as
  `application/manifest+json` and `text/javascript`. A `Service-Worker-Allowed`
  header only if a section scope needs it: both documents are served from
  inside the scope, so none is needed.

Icons
: From site files named in the settings (64, 192, 512, one maskable),
  validated present. When absent the manifest omits them and `lazysite check`
  warns. No icon generation.

Updates follow a deploy
: The worker's cache name includes the deployed engine release and a
  fingerprint of the cached shell files, so a deploy changes the worker and
  installed devices update (`skipWaiting` and `clients.claim`).

Caching rules (L1's constraints, non-negotiable)
: Precache only the app shell; scripts and styles stale-while-revalidate;
  images cache-first; never the Odoo endpoint, the manager, the auth
  endpoints, any page with an `odoo:` or `odoo-identity:` binding, any
  per-viewer page (anything sent `no-store` or `private`); the worker honours
  the response's Cache-Control and never stores such a response; it never
  touches cookies, tokens or answers. No offline queue, background sync or
  push.

Registration
: A small engine script added to pages in the app's scope when the feature is
  on.

# What shipped

`lazysite-processor/app.pm`, a part of the processor, holds the settings, the
manifest, the worker and the registration. Setting `app_name` turns the app on.

- `<scope>manifest.webmanifest` and `<scope>lazysite-sw.js` are generated on
  request, after a real file at the address and before the registries.
- `/assets/lazysite-app.js` (an engine asset, served on every domain) registers
  the worker; a page inside the scope gets it, with a `<link rel="manifest">`,
  at render time.
- The worker answers only a stylesheet or script (stale-while-revalidate) and
  an image (cache-first). It does not answer a page of any kind, a POST, a
  Range request, another origin, `/cgi-bin/`, any `lazysite-*.pl` endpoint,
  the engine tree, the manager path or the sign-in and sign-out paths. That is
  stricter than L1 asked for: because no page is ever stored, an `odoo:` page,
  a per-viewer page and a protected page cannot be, whatever headers they carry.
- A response is stored only if it is a whole 200 that is not opaque, not
  `Vary: *`, and not `no-store` or `private`; a copy stored earlier of a file
  that now says so is deleted.
- The shell is the engine's chrome, the registration script, the icons, the
  stylesheets and scripts the start page's cached render links, and `app_shell`.
  Its refused paths come from the same table as the worker's, so the shell
  cannot name an endpoint.
- A scope or start page the engine cannot honour turns the app off rather than
  being repaired; `lazysite check` names the value, a colour that is not hex, an
  icon the site does not serve, and an app with no icons.

Documented in `starter/docs/app.md` and `starter/docs/reference.md`.
Tests: t/unit/processor/133 (manifest from settings, off by default, both
levels, icons, the version and fingerprint), 134 (the worker driven in node with
a stand-in cache: refused paths, no-store and private, the strategies, install
and activate), t/unit/tools/82 (the check).

Left open: an offline queue, background sync and push were not asked. A page is
not available offline.
