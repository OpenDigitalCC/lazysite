status-note: "SHIPPED 0.10.33 - THE RULE IS REJECT, NOT TRUNCATE, and it is stated once in Domains::valid_presentation_name: a `layout:` or `theme:` value must match [A-Za-z0-9_-]+, which is the rule theme_config_issues, action_create_theme and the layout walkers already enforce and which nothing had written down where a READER could ask for it. Truncation was the worse of the two behaviours and the one that looked like agreement - `my` is a layout nobody wrote, it may well exist on the instance, and the reader handed it back as the ACTIVE layout, indistinguishable from a working answer; rejection says the site has no layout configured, which is true, which every caller already handles because it is the fresh-install state, and which leaves the operator's own text in the conf where they can see it. Domains::presentation_value is the single application point: _parse runs the two keys through it (an invalid base value resolves to unset, an invalid alias override leaves the domain INHERITING as if the line were never written) and _read_active_layout_and_theme now takes the WHOLE trimmed value - as _parse always did - and asks the same helper instead of its own \\S+ match and strip. Refusals are logged once per process per value, naming the key and the rule, so a site that renders unstyled says why. domain_set refuses the write for layout/theme, alongside its existing content_root/lang/lang_group checks, so the conf cannot acquire a value no reader will take. NOT COVERED: the processor's resolve_site_vars (lazysite-processor.pl) is a THIRD reader of the same key and was not in this branch's ownership - it takes the whole line, so it agreed with _parse before this change and no longer does; an invalid name resolves to a layout directory that does not exist either way, so the rendered outcome is unchanged, but the rule should reach it. The Backups.pm comment misplacement noted at the end of this filing is also NOT addressed here. t/unit/manager/113 reads one conf value with a space through both surfaces and asserts one answer. ORIGINAL NOTE: FOUND 2026-08-25 during the SM516 cleanup wave, proven by probe (tmp/tlo3-probe.pl): the review's TLO-3 proposed folding _read_active_layout_and_theme onto Domains::_parse as duplicate conf reading. They are not equivalent - _read_active_layout_and_theme matches \\S+ then strips to [A-Za-z0-9_-], while Domains::_parse takes the whole trimmed line - so a value containing a space resolves differently depending on which reader asks. The agent refused the row rather than unify them, which would have chosen a winner silently. WHICH IS RIGHT IS THE QUESTION: a layout or theme name containing a space is almost certainly invalid, in which case the stricter reader is correct and the permissive one should refuse rather than truncate; but nothing currently says so, and an operator who writes one gets a different answer from each surface. PLANNED for 0.10.33: decide the rule (probably: reject the value, do not truncate it), state it once, and have both readers use it. ALSO NOTED, same shape, not filed separately: in Backups.pm the 'Filesystem paths are never exposed' comment heads _archive_scope but describes _scrub_paths."

# The proving test

One conf value with a space, read through both surfaces, gives the same
answer - or is refused by both with the same message.
