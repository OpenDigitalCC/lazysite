# The measurement

| Tree | Files | Bytes |
| --- | --- | --- |
| `docs/feature-requests` + archive | 622 | 3.2 MB |
| `starter/docs` (ships to every site) | 32 | 403 KB |
| everything else under `docs/` | 65 | ~700 KB |
| **total** | **719** | **~4.3 MB** |

Reading it is on the order of a million tokens. **An agent asking "is there a
document about X" had no answer short of grepping, and grep does not work when
you do not yet know the vocabulary.**

# What was built

`tools/gen-doc-index.pl` walks the doc trees and emits `docs/INDEX.md`: eleven
trees, each with a line saying what it is FOR, then one row per document with
its title and a one-sentence summary. **102 documents, 19KB** - about 200 times
smaller than the corpus it maps.

`t/lint/110` holds it true, and does so by **running the generator and diffing**
rather than re-implementing the listing. A test that re-implemented it could
disagree with the tool about what the index should contain; this one can only
disagree about whether the committed file says it.

## Two things it deliberately does not do

**It does not list the feature requests.** `tools/backlog.pl` already lists them
from the status headers `t/lint/09` enforces, with `--all` and `--json`.
Duplicating 622 entries would create exactly the hand-kept second copy the index
exists to avoid. The index names the tool; the lint asserts that no SM appears
in it.

**It does not invent front matter.** 48 files carry none - the top-level manuals
among them - so the generator falls back to the first heading and the first
sentence of the first paragraph. An index that skipped them would omit the
documents a new reader most needs.

## One thing that had to be fixed to make it useful

The first version took the first prose LINE as the summary, and these files are
hard-wrapped, so `OPERATOR.md` was summarised as "Install/first-run is in". A
line is not a thought. It now reads the first paragraph and takes its first
sentence.

# What remains, and it is the larger half

The release manager's question was about documentation management, not only this
repository. Docs also live:

- in the **layouts catalogue**, its own repository
- in a **running site's published pages** - around thirty, reachable through
  `describe_capabilities`
- on the **website**

`docs/INDEX.md` names these and reaches none of them. **A cross-tree index needs
each tree to expose a listing the others can consume** - which is a design
question about what that listing looks like, not a second script. Worth deciding
before anyone writes one, because the wrong answer is three more generators that
disagree.
