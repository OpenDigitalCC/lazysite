# SM188 - Session-marker desync causes a login redirect loop

## Symptom

A logged-in user finds every page redirects to `/login`; the login page says
"You are already signed in" and shows no login form; any manager URL redirects
too. Clearing the browser cache does not help. The user is stuck with no way to
re-authenticate.

## Root cause

Login sets TWO cookies:

- `lazysite_auth` - the HMAC-signed session the auth wrapper (`lazysite-auth.pl`)
  validates on every request: signature, expiry, account-disabled,
  session-revoked. Only when all pass does the wrapper set `X-Remote-User` +
  `LAZYSITE_AUTH_TRUSTED` and exec the processor.
- `lzs_session=1` - a NON-signed, JS-readable marker cookie (set at login,
  cleared at logout). A UI hint only; it carries no authority.

`starter/login.md` decides "already signed in" versus the login form purely from
the JS marker (`data-ls-auth-out` / `data-ls-auth-in`), NOT from the real
validated session. So when the real session becomes invalid while the marker
persists, the two desync into a loop:

1. The wrapper rejects `lazysite_auth` (bad signature / revoked / disabled /
   expired) - so no `X-Remote-User` is set.
2. Any `auth: required` or manager page sees `!authenticated` and 302s to
   `/login` (`lazysite-processor.pl` `check_auth`). The bounce does NOT clear the
   marker.
3. `/login` JS sees `lzs_session=1`, shows "already signed in" and HIDES the
   login form - so there is no way to re-authenticate - and any link leads back
   to step 1. Loop.

Clearing the browser CACHE does not remove the marker COOKIE, so the loop
survives a cache clear (cache is not cookies).

## What makes the real session go invalid (the trigger)

- EVERY logged-in user affected at once points to the cookie-signing secret
  changing: `lazysite/auth/.secret` regenerated by a site rebuild/restore, or
  `rotate-auth-secret`, which invalidates every existing cookie (logged as
  `auth: signature mismatch`).
- A SINGLE user points to `auth: session revoked` (an operator sign-out, or a
  sign-out-everywhere / `not_before` marker), `auth: account disabled`, or
  `auth: cookie expired`.

## Fix

Reflect the REAL session state, and never trap the user:

1. Clear the marker on rejection. When the wrapper rejects a session (any reject
   branch) and the request bounces to `/login`, emit
   `Set-Cookie: lzs_session=; Max-Age=0` so the login page shows the form. The
   bounce in `check_auth` (and the wrapper's own reject path) is the natural
   place to attach it.
2. Drive the login page from the server, not the marker. Additionally, decide
   "already signed in" versus the form from the server's `[% authenticated %]`
   (the real validated identity), not the JS marker, so a dead session always
   shows the form.
3. Belt-and-braces: the "already signed in" branch should always offer a
   prominent "sign in as someone else / sign out" that clears both cookies, so a
   trapped user has an escape hatch even before the fix ships.

## Operator remediation (now, pre-fix)

- Affected user: visit `/logout` (it clears BOTH cookies) then sign in; or clear
  COOKIES (not cache) for the site.
- Everyone affected: check the site's auth log for mass `signature mismatch`. If
  the `.secret` changed, a fresh login fixes it - but the marker trap blocks the
  fresh login, so users must clear cookies or hit `/logout` first.

## Tests

- A request whose `lazysite_auth` is signature-invalid (or revoked / disabled)
  bounces to `/login` AND the response clears `lzs_session`; the login page then
  renders the form, not "already signed in".
- Regression: a valid session is unaffected - the marker is kept and no bounce
  occurs.

Related: SEC-2026-07 (M4/M5 server-side session revocation), the auth wrapper's
cookie-verify path, `starter/login.md` (`data-ls-auth-*`).
